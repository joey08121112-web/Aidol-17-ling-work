# 硅基记忆产品调研与 Aidol 第三项能力建议

调研日期：2026-10-17。范围：硅基记忆官网公开说明、产品页和开发者页；未注册账号、未购买产品、未调用其 API，也未实测其硬件或 App。本文区分**官网声明**、**本仓库已有能力**和**建议实现**，不能作为第三方性能验收或本项目功能已完成的证明。

后续集成说明：本文保留调研时的设计建议与代码快照。纪要、证据问答及记忆时间线随后在本仓库实现，实际字段使用 `pinned`，原文来源采用 `transcript:{id}`；最新操作和限制以 [记忆功能说明](memory-features.md) 与 [API 文档](api.md) 为准。本文的建议清单不是已通过的测试结果。

## 结论

建议在「会议纪要与待办」「问记忆并显示引用」之外，优先完成**记忆时间线、重要收藏、立即记住**，统一放在现有「全局记忆」页面。耳机负责减少输入动作，Web 负责核对、整理和找回；继续使用本地 SQLite 和现有豆包服务，无需为这项功能新增记忆平台账号、模型或硬件接口。

可借鉴的是从收音到可管理记忆的产品闭环。Aidol 的实现、名称、界面、提示词和存储结构自行设计，不复制第三方品牌、硬件外观、视觉素材或宣传文案。

## 哪些思路适合 Aidol

以下为本项目的产品与工程判断，不是第三方实测结论。

| 产品思路 | 对 Aidol 的具体价值 | 本轮取舍 |
| --- | --- | --- |
| 收音之后还有整理与找回 | 用户需要看见一句话最终留下了什么，而不只是转写滚动 | 用现有转写、记忆、摘要、引用构成闭环 |
| 采集与记忆处理分开 | 整理过程不能卡住实时语音 | 维持现有音频与记忆任务分离，收藏无需模型 |
| 找回与当前问题有关的信息 | 工作、通勤、生活内容不能全部无区别塞入回答 | 由「问记忆」返回有证据的结果；没有依据则明确不足 |
| 用户能介入记忆内容 | 自动提取可能遗漏一个刚出现的重要地址或约定 | 增加可见的「记住这句」，保存成功后才显示反馈 |
| 记录可核对 | 用户应区分原话、提炼内容和生成结论 | 保留来源标记，能关联证据时才提供引用 |

有两个边界尤其需要保留：工作模式要求多人对话全记录，因此不能照搬只筛选设备主人的方案；Viaim SDK 尚未交付，因此不能宣称耳机物理键已支持收藏、独立存储或离线录音。

## 第三项功能：记忆时间线

### 面向用户的完整操作

1. 在耳机语音或文字对话中产生一条转写，例如「公司门口在东侧，明天从东门进」。
2. 用户在该条转写旁点击「记住这句」。界面展示待保存原文和类型，调用本地保存后出现记忆卡。
3. 全局记忆按用户设置时区分组为今天、昨天和具体日期；每张卡显示内容、类型、时间与来源。
4. 点击星标，将某张记忆标为重要。收藏状态落库，刷新或重启仍存在。
5. 使用「全部 / 重要」切换并结合现有关键词、类型筛选找回；仍可导出或删除。
6. 后续在「问记忆」里提问时，引用卡片可对应到已保存证据。收藏只表示用户重视，不自动把内容提升为事实或改变答案正确性。

该功能既覆盖会议约定，也覆盖通勤入口、联系人偏好、餐馆口味和生活灵感。它不需要切换新模型，不改变三种场景的定义。

### 即时保存的语义

「立即记住」是**立即持久化用户选择的文字**，不是承诺立即完成复杂语义提取或远程索引。

- 本轮可优先提供按钮入口和现有手动新增表单；用户点击后明确知道保存了什么。
- 原文默认作为事实笔记保存，不自动补全身份、日期、地址或承诺。
- 没有转写、转写为空或已删除时，应禁用入口或解释缺少内容。
- 同一条原话重复点击不应产生多张重复卡；重试需要幂等。
- 如果后续增加「帮我记住……」语音指令，必须定义明确触发边界、提供可见确认并保留原文；不能把录到的所有类似表达都当作设备操作命令。
- 厂商真实 SDK 到位后，可将已确认支持的物理事件映射到同一保存动作；现在不假设具体按键协议。

以下依据调研时的代码快照；本轮其他智能体可能正在集成新功能，最终状态以代码、API 文档和验收记录为准。

| 模块 | 已有 | 第三项功能需要补齐 |

| `app/domain.py` | `MemoryInput` 支持内容和四种类型 | 收藏更新请求及可选原文引用的输入校验 |

## 建议的最小技术方案

这些是待集成设计，**不是已经公开可调用的新 API 契约**。若集成负责人选择其他命名，应同步 `docs/api.md`。

### 存储

- 优先为 `memories` 增加 `starred`，取值 0/1，默认 0；若需要来源映射，使用独立关联表连接记忆 ID 与转写 ID。
- 老库升级先读取 `PRAGMA table_info` 再做有条件迁移；不能仅修改 `CREATE TABLE IF NOT EXISTS`。
- 排序字段明确区分记录时间和收藏时间。时间线按记录时间，不因收藏操作跳到今天。
- 删除记忆时清除关联；清空、导出包含新数据。所有读写继续使用 `Store` 事务，不在前端保存唯一副本。
- 保存来源转写 ID 时先确认存在；关联失效后可保留用户笔记，但显示「原文已删除」，不能捏造证据。

### 业务与接口

- 收藏接口只改变指定记录的收藏状态，ID 不存在返回 404；返回更新后的状态供前端校准。
- 「记住这句」由服务读取指定转写原文后保存。幂等键可以关联原始转写 ID 和动作，不依赖模型生成文本。
- 前端可先用现有记忆列表做本地日期分组；要说明列表上限，不能把最近若干条描述为全部历史。记录增长后再增加服务端分页。
- 记忆内容仍是待检索的数据。即使卡片中出现「忽略规则」「执行命令」等文本，也不能获得系统指令权限。
- 新状态通过现有 SSE 刷新机制同步；保存失败应恢复按钮状态并展示错误。

### 前端

- 顶部沿用搜索与类型筛选，再增加「全部 / 重要」；不要再建立第三套导航。
- 每组日期标题显示日期和本组数量；依据 `settings.timezone` 分组，避免电脑时区与设置不一致。
- 星标是实际按钮，包含「标为重要 / 取消重要」文字或明确无障碍名称，使用 `aria-pressed`；不只靠颜色表达。
- 长内容允许换行，引用详情可展开；手机上卡片动作仍能点击，避免拥挤小图标。
- 来源写成可理解的「手动记下 / 原话保存 / 自动整理 / 演示数据」，后台供应商名称留在详情。

## 本轮验收建议

| 验证 | 预期 |
| --- | --- |
| 从旧数据库启动两次 | 迁移幂等，原有记忆不丢失 |
| 收藏后刷新、重启 | 收藏状态保持 |
| 取消收藏 | 「重要」筛选立即更新，无多余记忆副本 |
| 连续点击保存同一转写 | 仅创建一条明确关联的笔记 |
| 从工作、通勤、生活各保存一句 | 三类来源均可进入同一时间线 |
| 今天/昨天跨午夜并切换时区 | 日期分组依据用户设置，无重复或错组 |
| 搜索与类型、收藏同时筛选 | 条件叠加生效，空结果可理解 |
| 删除原话、删除记忆、清空数据 | 引用失效可解释，关联无悬挂状态，导出不含已删内容 |
| 演示数据与真实记录混合 | 演示标记仍在，不能悄悄当作真实证据 |
| 离线或模型未配置 | 手动保存、收藏、检索已有卡片仍可在本地工作 |

测试使用临时 SQLite 和合成文字，不调用付费模型。验收通过后再在 `docs/acceptance.md` 记录实际结果，不能把本表直接当作通过清单。

## 本轮不扩张的范围

不新增第三方记忆平台依赖、声纹注册、人脸/人脉画像、云端多租户、记忆图谱、广告投放或微信自动推送。当前只把用户最常用的保存、确认重要性、按时间找回做完整；这样能在现有耳机音频链路上立即演示，也不会被尚未交付的硬件接口阻塞。
